# NVMe Identify 검증 하네스 — 설계

- 작성일: 2026-10-20
- 상태: 초안 (사용자 검토 대기)

## 1. 의도와 배경

현재 Identify(id-ctrl, id-ns 등) 검증은 다음 세 가지를 사람이 직접 대조하는 방식이다.

1. nvme-cli로 뽑은 로그를 **기존에 검증했던 로그**와 비교한다.
2. **사내 정책 페이지**의 값과 비교한다.
3. **스펙 문서**(NVMe, OCP)에서 해당 필드의 정의를 찾아본다.

가장 큰 문제는 **기존 로그를 정답으로 쓴다는 점**이다. 기존 로그와 값이 같아도 다음과 같은 이유로 정답이 아닐 수 있다.

- FW가 지원하는 스펙 버전이나 기능이 바뀌었다.
- 사내 정책이 바뀌었다.
- 애초에 기존 검증이 틀렸다.

이런 경우를 확인하려면 스펙과 정책을 여기저기 뒤져야 해서 시간이 가장 많이 든다.

**이 하네스의 목표는 비교 기준을 "이전 로그"에서 "현재 맥락(스펙 버전, 정책, 제품 정보)에서 이 필드가 가질 수 있거나 가져야 하는 값"으로 바꾸는 것이다.**

이를 위해 스펙별 전문 에이전트가 필드별 규칙을 미리 규칙 DB로 쌓아 둔다. 규칙에는 다른 필드와의 관계도 포함된다. 검증할 때는 이 규칙 DB를 기준으로 기계적으로 판정한다.

## 2. 목표 / 비목표 / 실패 조건

### 목표
- **필드별 허용값 규칙 DB를 만든다.** 각 규칙에는 다음 정보가 붙는다.
  - 근거(출처 문서, 섹션, 페이지)
  - 출처의 버전
  - 다른 필드와의 관계(조건)
  - 예: "NVMe: 필드 A는 필드 B가 1일 때만 0이 아닌 값을 가진다"
  - 예: "OCP: 필드 A는 3 이하의 값을 갖는다"
- **스펙마다 전문 에이전트를 둔다.** 처음에는 NVMe와 OCP 두 개다. 새 스펙이 추가되면 같은 틀로 전문 에이전트를 하나 더 만든다.
- **검증은 규칙 DB만 보고 결정론적으로 판정한다.** 같은 입력을 넣으면 늘 같은 결과가 나와야 한다. 결과에는 근거가 함께 나온다.
- 기존 로그는 버리지 않고 **보조 신호(CHANGED)**로 쓴다.
- 판정이 틀렸을 때 **규칙을 고치는 흐름**을 마련하고, 고친 이력을 남긴다.
- 나중에 사내 정책을 붙일 수 있게, 규칙 형식에 출처, 버전, 우선순위 자리를 처음부터 둔다.

### 1차 범위 (오늘 이후 첫 구현)
- 다루는 스펙: **NVMe Base 2.1, NVM Command Set 1.1, OCP Datacenter NVMe SSD 2.6** (이 조합이 기본값)
- 다루는 구조: **id-ctrl (CNS 01h), id-ns (CNS 00h)**
- 구조를 넘나드는 관계 규칙도 처음부터 지원한다. 예: id-ns의 필드가 id-ctrl의 값을 참조하는 경우.
- **1차 완료 기준 (사용자 결정):** id-ctrl과 id-ns의 **모든 필드와 비트**를 다룬다. PSD, LBAF 배열도 포함한다.
  - 레이아웃과 규칙을 모두 추출하고 `rule-verifier` 교차 검증까지 마친다.
  - 이 두 구조와 관련된 OCP 2.6 요구사항도 규칙으로 들어간다.
  - 엔진, 에이전트, 실행 흐름, 수정 흐름이 끝까지 동작해야 한다.
  - 진행 순서는 빌더가 정한다. 다만 먼저 한 필드 묶음으로 전체 흐름을 관통시킨 뒤 일괄 추출하는 것을 권장한다.

### 비목표 (1차에서는 하지 않음)
- **사내 정책 구현.** 이번에는 러프한 계획만 세운다(§9).
- 다른 Identify 구조(CNS 06h, id-ns-cs, granularity 등). 다만 구조 이름과 레이아웃만 추가하면 확장되도록 설계한다.
- 팀 공유용 리포트나 대시보드. 결과는 사용자 혼자 보고 판단한다.
- 테스트 PC에 에이전트나 런타임을 설치하는 것.

### 실패 조건 (기술적으로 돌아가도 실패로 보는 경우)
- **근거 없는 판정.** 규칙에 출처 위치가 없어서 사람이 확인할 수 없으면 실패다.
- **틀린 규칙이 조용히 PASS나 FAIL을 만드는 것.** 그래서 규칙에 신뢰 상태를 붙이고, 그 상태를 결과에 노출해야 한다.
- **규칙이 없는 필드를 PASS처럼 보이게 하는 것.** 그런 필드는 반드시 NO-RULE로 드러나야 한다.
- **판정할 때마다 결과가 달라지는 것.** 그래서 LLM이 판정하지 않는다.

## 3. 제약

- **환경 구성**
  - 오피스 PC: Windows. 외부 네트워크와 Claude Code를 쓸 수 있다.
  - 테스트 PC: 오피스 PC에서 ssh로 접근한다. 오피스 PC의 Claude도 테스트 PC에 접근할 수 있다.
- **설치된 도구**
  - 오피스 PC에는 Python이 없다. `uv`와 `node`, OpenSSH 클라이언트는 있다.
  - 테스트 PC는 **Linux**이고 nvme-cli가 있다. nvme-cli 버전은 아직 모른다. 실행할 때 `nvme version`으로 기록한다.
  - sudo는 **비밀번호 없이** 실행된다.
- **검증할 드라이브는 사용자가 매번 `/dev/nvmeX`로 지정한다.** 자동으로 고르지 않는다.
- **namespace는 활성화된 것만** 확인한다. NSID FFFFFFFFh와 비활성 namespace는 1차에서 제외한다.
- **기존 로그는 nvme-cli 텍스트 출력**이다. JSON이 아니다.
  - 실제 샘플은 아직 없다. 1차에서는 nvme-cli 기본 텍스트 출력 형식을 흉내 낸 **임의 로그를 만들어** 파서와 CHANGED 비교를 테스트한다(사용자 결정).
  - 실제 로그가 들어오면 파서를 맞춰야 할 수 있다. 그래서 리포트에 CHANGED는 "합성 샘플로만 검증됨" 상태라고 문서화해 둔다.
- **스펙 원본은 `spec/` 폴더에 PDF와 md가 쌍으로 있다.** md는 pdf2md로 변환한 것이다.
  - 필드 표는 대체로 잘 살아 있다.
  - 다만 **페이지를 넘어가는 표에서 비트 단위 하위 표가 깨진다.** 가짜 열(`Col6/Col7/Col8`)이 생기고 설명이 2~3번 중복된다. NVMe Base의 OAES, CTRATT 등이 그렇다.
  - 그래서 md만 믿으면 안 되고, PDF 페이지와 교차 확인해야 한다.
- **OCP 2.6은 `NVMe-1`에서 NVMe Base 2.0e / NVM CS 1.0e 준수를 요구한다.** 하지만 사용자가 정한 기본값은 Base 2.1 / NVM CS 1.1이다. 버전 차이로 생기는 불일치는 규칙에 메모로 남긴다.
- **사내 정책 원본은 사내 보안 때문에 Claude가 직접 읽을 수 없다.** 사용자가 복사해서 붙여넣어야 한다. 정책 형식은 엑셀이나 문서로 일정하지 않고, 사용자가 형식에 관여할 수 없다.
- **사용자는 규칙을 하나하나 검토할 여력이 없다.** 에이전트 교차 검증만으로 일단 쓰고, 실제 검증에서 걸리면 고친다.
- **우선순위는 정책 > 스펙**이다(사용자 결정). 스펙 안에서는 OCP > NVMe로 둔다(OCP가 NVMe 위에 얹는 추가 요구사항이기 때문).

## 4. 전체 구조

```
[오피스 PC (Windows)]
  Claude Code
   ├─ 스펙 전문 에이전트 (nvme-spec-expert, ocp-spec-expert, [policy-expert: 추후])
   ├─ 교차 검증 에이전트 (rule-verifier)
   ├─ 규칙 DB (repo 안의 구조화된 파일)
   ├─ 검증 엔진 (Python, uv로 실행, LLM 없음)
   └─ 검증 실행 진입점 (Claude Code skill/command)
        │ ssh
        ▼
[테스트 PC]
   nvme-cli만 사용. 덤프만 만들고 아무것도 설치하지 않는다.
```

역할은 두 단계로 나뉜다.

- **규칙을 만드는 단계 (LLM).** 스펙 에이전트가 원본 문서를 읽고 규칙 DB를 생성하거나 고친다.
- **검증 단계 (결정론).** 엔진이 덤프, 제품 정보, 규칙 DB를 받아 판정한다.
  - LLM은 결과를 요약하고, 애매한 건을 설명하고, 규칙 수정 요청을 처리하는 보조 역할만 한다.

## 5. 데이터 모델

### 5.1 구조 레이아웃 (layout)

스펙 버전마다, 구조마다 필드 정의를 둔다. 각 필드에는 다음이 들어간다.

- 바이트 오프셋과 길이
- 필드 약어와 이름
- 비트필드 정의
- M/O/R 구분 (I/O, Admin, Discovery 컨트롤러 별)
- reserved 영역
- 배열 구조. 예: id-ctrl의 PSD[0..31], id-ns의 LBAF[0..63]

엔진은 이 레이아웃으로 **원시 바이너리 덤프를 디코드**한다. 레이아웃 역시 NVMe 스펙 에이전트가 뽑고 교차 검증을 거친다.

### 5.2 규칙 (rule)

규칙 하나의 모양은 다음과 같다. 필드 구성은 확정이고, 구체적인 문법은 빌더가 정한다.

```yaml
- id: OCP-NVMe-CFG-14
  source: ocp-2.6              # nvme-base-2.1 | nvm-cs-1.1 | ocp-2.6 | policy-<개정판>
  ref: "NVMe-CFG-14, p.xx"     # 근거 위치 (섹션/페이지/요구사항 ID/정책 시트·행)
  target: id-ctrl.SQES[7:4]    # 구조.필드[비트] — 배열 원소 지정 가능
  when: always                 # 조건식. 예) id-ctrl.ONCS[3] == 1, profile.features.sanitize
  expect: "== 6"               # ==, !=, in {...}, range, !=0, ascii, reserved==0, 다른 필드 참조
  level: shall                 # shall → FAIL, should → WARN
  status: cross-checked        # cross-checked | uncertain | corrected
  note: ""                     # 버전 차이 등 메모
  history: []                  # 수정 이력 (이전 규칙, 이유, 날짜)
```

- **`when`과 `expect`에서 다른 필드를 참조할 수 있다.** 다른 구조(id-ns가 id-ctrl을 참조하는 경우 등)와 제품 정보(`profile.*`)도 참조할 수 있다. "B가 1일 때만 A가 0이 아니다" 같은 관계가 이것으로 표현된다.
- **reserved 비트/영역이 0이어야 하는 규칙, 정의되지 않은 값이 들어가면 안 되는 규칙**은 레이아웃에서 기계적으로 생성할 수 있다. 직접 쓰든 생성하든 빌더가 정한다.
- 식은 `eval` 없이 작은 전용 문법으로 해석한다. 규칙 파일을 신뢰할 수 없는 입력으로 다룬다.

### 5.3 제품 정보 (profile)

- 기준 스펙 버전 조합을 담는다. 기본값은 `nvme-base-2.1 + nvm-cs-1.1 + ocp-2.6`이다.
- 제품이 지원해야 하는 기능 목록을 담는다. 예: namespace management, sanitize.
- 제품별로 기대하는 고정 값을 담는다. 예: VID, SSVID, IEEE OUI. MN 패턴 등도 필요하면 넣는다.
- 제품 정보는 사용자가 제공한다. 기본 프로필 하나를 두고, 제품별 프로필은 기본에서 다른 부분만 덮어쓴다.

### 5.4 우선순위와 충돌

- **기본은 누적이다.** 한 대상에 적용되는 규칙은 출처와 상관없이 모두 평가하고, 모두 만족해야 PASS다. OCP 규칙은 대부분 NVMe 위에 제약을 더하는 것이라서 NVMe 검사를 지우면 안 되기 때문이다.
- **덮어쓰기는 명시적으로만 한다.** 상위 출처 규칙이 `overrides: [하위 규칙 id...]`를 선언했을 때만 그 하위 규칙을 판정에서 뺀다. 상위 출처의 순서는 **policy > ocp > nvme(base, nvm-cs)**다. 빠진 하위 규칙은 결과에 "overridden: 스펙과 다르지만 상위 출처에 따라 판정"으로 표시한다. 정책(Spec Gap)은 본래 "스펙과 다른 부분" 목록이라 이 방식과 잘 맞는다. 비트 범위가 겹치는지 계산하지 않고 규칙 id로 지정하므로, 엔진에 겹침 계산이나 solver가 필요 없다.
- **선언 없는 충돌은 런타임에 잡는다.** 같은 값에 대해 출처가 다른 두 규칙 중 하나는 통과하고 하나는 실패하면, 그 필드는 FAIL로 처리하되 "검토 필요(규칙 충돌 가능)"를 붙이고 두 규칙을 모두 보여준다. 같은 출처 안에서 이런 일이 생기면 규칙 DB 오류로 보고한다.
- `overrides`가 가리키는 규칙 id가 존재하지 않거나, 하위 출처가 상위 출처를 덮으려 하면 규칙 DB 로드 단계에서 오류로 처리한다.

### 5.5 규칙 종류와 커버리지

- 규칙에 `kind`를 둔다. `value`는 실제로 기대되는 값을 확인하는 규칙이고, `format`은 reserved==0, 정의된 값 범위, ASCII처럼 형식만 확인하는 규칙이다.
- 어떤 필드에 `format` 규칙만 적용됐으면 PASS 대신 **PASS(형식만)**으로 표시한다. 형식만 맞았는데 검증된 것처럼 보이지 않게 하기 위해서다.
- 커버리지는 **비트 단위**로 계산한다. 예를 들어 OACS 16비트 중 몇 비트에 `value` 규칙이 있는지를 센다.
- **"제품이 기능 X를 지원하면 필드 비트 Y가 1이어야 한다"** 같은 규칙(예: `profile.features.sanitize` → SANICAP)은 해당 비트를 정의한 스펙의 에이전트가 쓴다. 출처는 그 스펙으로 하고, 조건은 `when: profile.features.<x>`로 표현한다. 대부분의 capability 비트는 이 규칙이 있어야 의미 있는 PASS가 된다.

## 6. 판정 등급과 리포트

| 등급 | 의미 |
|---|---|
| FAIL | shall 위반, 또는 들어갈 수 없는 값 |
| WARN | should 위반 |
| PASS | 해당 필드에 적용되는 규칙을 모두 만족 |
| NO-RULE | 적용되는 규칙이 없는 필드 (규칙 DB의 빈 곳을 드러냄) |
| CHANGED | 기존 로그와 값이 다름 (판정과는 별개의 참고 정보, 다른 등급과 함께 붙음) |

- 결과에는 필드마다 실제 값, 기대 값, 적용된 규칙 ID, 근거(출처/섹션/페이지), 덮어쓴 규칙이 표시된다.
- **`uncertain` 상태의 규칙으로 판정된 항목은 따로 표시한다.** 의심해야 할 곳이 보이게 하기 위해서다.
- 터미널에는 FAIL/WARN 중심으로 요약해서 보여준다. 전체 리포트는 마크다운 파일로 실행 폴더에 저장한다.
- 규칙 커버리지 요약도 함께 낸다. 전체 필드 중 몇 개에 규칙이 있는지, NO-RULE이 몇 개인지를 보여준다.

## 7. 에이전트

Claude Code 서브에이전트(`.claude/agents/*.md`)로 정의한다.

| 에이전트 | 역할 |
|---|---|
| `nvme-spec-expert` | NVMe Base + NVM Command Set 담당. 레이아웃과 규칙을 추출하거나 고친다. 규칙 수정 요청에 답한다. |
| `ocp-spec-expert` | OCP Datacenter 스펙 담당. 요구사항 ID 단위로 규칙을 추출하거나 고친다. |
| `rule-verifier` | 다른 에이전트가 뽑은 레이아웃/규칙을 **원본 PDF 페이지와 독립적으로 대조**한다. 결과로 `cross-checked` 또는 `uncertain` 상태를 매긴다. |
| `policy-expert` | **추후.** §9 참조. |

- **새 스펙을 추가하는 방법.** 같은 틀의 `<spec>-expert` 정의를 하나 추가하고, `spec/`에 원본을 넣고, 출처 ID를 등록한다. 이 절차를 문서화해 둔다.
- 스펙 에이전트는 **md로 위치를 찾고, PDF 해당 페이지로 확인**한다. md에서 표가 깨진 구간이 있기 때문이다.

## 8. 작업 흐름

### 8.1 규칙 구축
1. 스펙 에이전트가 필드 묶음 단위로 레이아웃과 규칙을 추출한다. 필드 묶음의 예는 id-ctrl의 "Controller Capabilities and Features" 같은 섹션이다.
2. `rule-verifier`가 PDF 페이지와 대조해서 상태를 매긴다.
3. 결과를 규칙 DB에 커밋한다. 사용자 검토는 필수가 아니다.

### 8.2 검증 실행
1. 사용자가 Claude Code에서 "테스트PC `<host>`, 장치 `/dev/nvmeX`, 제품 `<profile>` 검증"을 요청한다.
2. ssh로 테스트 PC에서 `sudo nvme ...`를 실행한다. id-ctrl과 **활성 namespace 각각의 id-ns**에 대해 **바이너리 덤프와 텍스트 출력을 함께** 받는다. `nvme version`도 기록한다. 받은 결과는 `runs/<날짜>_<host>/`에 저장한다.
   - **판정은 바이너리를 레이아웃으로 디코드한 값으로 한다.** nvme-cli 버전마다 텍스트/JSON 필드명이 다를 수 있기 때문이다.
3. 엔진이 판정한다. `baselines/<제품>/`에 기존 텍스트 로그가 있으면 파싱해서 CHANGED를 붙인다.
4. 요약을 보여주고 리포트를 저장한다.

### 8.3 규칙 수정 (실제 검증에서 걸렸을 때)
1. 사용자가 "이 판정 틀렸어, 이유는 …"라고 말한다.
2. 해당 출처의 스펙 에이전트가 근거를 다시 확인하고 규칙을 고친다. 상태를 `corrected`로 바꾸고 `history`에 이전 규칙, 이유, 날짜를 남긴다.
3. 같은 런을 다시 판정해서 결과가 바뀌는지 확인한다.

## 9. 사내 정책 (러프 계획 — 1차 구현 대상 아님)

- **입력은 사용자가 붙여넣은 텍스트**다. 초기 파일 내용이든 개정 공지든 같은 경로로 받는다.
- `policy-expert`는 붙여넣은 내용을 같은 규칙 형식으로 정규화한다. 출처는 `policy-<개정판>`으로 표시하고, `ref`에는 시트/행이나 공지 식별자를 넣는다.
- **개정 공지가 오면** 기존 정책 규칙과 비교해서 변경, 추가, 삭제 목록을 보여준다. 사용자가 승인하면 반영한다.
- **나중에 수정된 파일이 오면** 공지로 반영한 내용과 대조해서 불일치를 알린다.
- 판정에서는 정책이 스펙보다 우선한다(§5.4).

## 10. 빌더에게 맡기는 것

- 규칙/레이아웃 파일의 구체적인 포맷(YAML이나 JSON)과 디렉터리 배치
- 조건식/기대값 식의 문법과 파서 구현
- 레이아웃에서 기계적으로 생성할 규칙의 범위
- ssh 실행 방식, nvme-cli 명령 옵션, namespace를 나열하는 방법
- 기존 텍스트 로그 파서의 구현
- 리포트 마크다운의 세부 모양
- 검증 실행 진입점의 형태(skill이든 slash command든)
- 엔진 테스트 전략. 합성 바이너리 덤프를 쓰는 단위 테스트가 기본이다.

## 11. 설계 중 내가 내린 결정 (사용자 확인 필요)

- 검증 엔진은 결정론적인 Python 스크립트로 만들고 uv로 실행한다. 오피스 PC에 Python이 없어서 이렇게 정했다. LLM은 판정하지 않는다.
- 판정은 nvme-cli 텍스트/JSON이 아니라 **바이너리 덤프를 디코드한 값**으로 한다.
- 스펙 내부 우선순위는 OCP > NVMe로 둔다.
- 테스트 PC에는 아무것도 설치하지 않는다. 오피스 PC에서 ssh로 명령만 실행한다.
- 판정 등급 구성(FAIL/WARN/PASS/NO-RULE/CHANGED)과 규칙 상태(cross-checked/uncertain/corrected). 사용자가 "괜찮다"고 함.
- 규칙은 기본적으로 누적 적용한다. 덮어쓰기는 `overrides`로 명시할 때만 한다. 명시 없이 출처끼리 결과가 엇갈리면 FAIL에 "검토 필요"를 붙인다(§5.4).
- 형식 규칙만 통과한 필드는 "PASS(형식만)"으로 표시한다. 커버리지는 비트 단위로 센다(§5.5).
- "기능 지원 → 비트" 규칙은 그 비트를 정의한 스펙의 에이전트가 쓴다(§5.5).
- `업무설계서.md`는 사용자 지시에 따라 이 설계에 반영하지 않았다.
